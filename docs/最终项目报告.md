# Minisys FmcPGA Minecraft TFT 体素渲染系统项目报告

## 摘要

本项目完成了一个面向 Minisys FPGA 开发板的 Minecraft 风格体素渲染系统移植与工程化实现。系统以 FmcPGA 体素渲染核心为基础，保留其 VHDL 渲染管线，在外围新增 Verilog 板级顶层、TFT 显示时序、帧缓冲读取适配、RGB444 到 RGB323 颜色转换、按键与拨码交互、手持方块 HUD、蜂鸣器音频、源码级 IP 替代模块和 Vivado 自动化脚本，使原本面向 VGA/原工程环境的体素渲染器能够在 Minisys 的 800x480 TFT 屏上显示并交互运行。

工程目标器件为 `xc7a100tfgg484-1`，主时钟为 100 MHz，TFT 输出为 RGB323，渲染核心帧缓冲为 320x240 RGB444。项目采用混合语言集成方案：通过 VHDL 扁平化封装模块将复杂 record 接口转化为普通端口，再由 Verilog 顶层接入 Minisys 板级资源。最终系统已经实现 3D 体素场景显示、玩家移动、视角旋转、方块选择、放置方块、挖掘方块、准星目标反馈、右下角手持方块显示、背景音乐、交互音效、JTAG 下载、SPI Flash 持久化烧录和静态检查。Vivado 实现结果显示，系统无 setup、hold、pulse width 失败端点，主要资源利用率为 LUT 43.17%、BRAM 56.67%、DSP 21.67%，能够满足课程设计演示与报告验收要求。

关键词：FPGA；Minisys；Vivado；TFT；体素渲染；Minecraft；VHDL；Verilog；硬件工程化

## 1. 绪论

### 1.1 项目背景

Minecraft 风格体素场景具有清晰的三维空间结构、方块地图、纹理采样、视角控制和交互修改等特点，适合作为 FPGA 图形系统课程设计的综合题目。相比简单彩条显示或二维图形实验，体素渲染系统需要同时处理坐标变换、射线步进、地图存储、纹理读取、颜色输出、帧缓冲和实时显示，对硬件结构、时钟、存储和时序都有较高要求。

原 FmcPGA 项目已经具备 Minecraft-like 体素渲染能力，但其目标工程环境、显示接口、IP 依赖和板级资源与本课程使用的 Minisys 开发板不完全一致。因此，本项目的主要任务不是从零重写渲染算法，而是完成一次完整的工程移植：将已有渲染核心接入 Minisys 的时钟、按键、拨码、TFT 屏、LED、蜂鸣器和配置存储器，并将工程整理为可复现、可构建、可测试、可说明的课程设计项目。

### 1.2 项目目标

本项目围绕“能在实际开发板上稳定演示的 FPGA 体素渲染系统”展开，主要目标如下：

1. 在 Minisys FPGA 开发板上实现 Minecraft 风格 3D 体素场景显示。
2. 使用 800x480 TFT 屏显示 320x240 渲染帧缓冲，并完成居中 2 倍放大。
3. 支持按键移动、视角旋转、方块选择、放置方块和挖掘方块。
4. 提供手持方块 HUD、准星目标反馈、LED 调试输出和蜂鸣器音频反馈。
5. 保留 FmcPGA VHDL 渲染核心，使用扁平化封装解决 VHDL 与 Verilog 顶层集成问题。
6. 使用源码级 Verilog 模块替代主要 Vivado IP，提高工程可复现性。
7. 提供 Vivado 工程创建、构建、下载、Flash 烧录和静态检查脚本。
8. 建立需求、测试和实现之间的追踪关系，便于验收和后续维护。

## 3. 总体设计

### 3.1 系统总体架构

系统采用“Verilog 板级外壳 + VHDL 渲染核心”的混合语言结构。板级 Verilog 顶层负责 Minisys 外设、TFT 输出、蜂鸣器和 LED 调试；VHDL 核心负责体素场景渲染、玩家状态、地图修改、准星目标和帧缓冲写入。

```text
Minisys 时钟/按键/拨码/引脚
  -> Verilog 板级顶层
  -> TFT 时钟与 800x480 时序
  -> 帧缓冲读地址映射
  -> VHDL 扁平化核心封装
  -> FmcPGA 渲染/控制/地图/纹理管线
  -> 320x240 RGB444 双缓冲
  -> 手持方块 HUD 叠加
  -> RGB444 到 RGB323 转换
  -> TFT RGB323 输出
```

该架构的优点是迁移风险低。FmcPGA 渲染管线包含坐标计算、射线步进、地图读取、纹理采样和颜色累积，若一次性全部重写为 Verilog，容易引入算法错误和时序问题。因此项目先保留已验证的 VHDL 核心，把与开发板相关的输入输出、显示适配和工程自动化放在外围实现。

### 3.2 数据流设计

渲染核心在管线时钟下根据玩家位置、视角、地图和纹理数据生成 320x240 RGB444 帧缓冲。TFT 像素时钟独立工作，以 800x480 扫描可视区域。读映射模块根据当前 TFT 像素坐标计算源帧缓冲地址，在有效区域内读取对应 RGB444 像素，在左右边界输出黑色。

当前显示映射规则为：

```text
if 80 <= pix_x < 720 and pix_y < 480:
    src_x = (pix_x - 80) >> 1
    src_y = 239 - (pix_y >> 1)
    addr = src_y * 320 + src_x
else:
    output black
```

其中 `src_y` 采用翻转处理，用于匹配最终 TFT 显示方向。读取出的 RGB444 像素先经过手持方块 HUD 叠加，再经过 RGB323 截断输出到 TFT。

### 3.3 控制流设计

用户通过 Minisys 按键和拨码开关完成交互。S1-S4 在 `sw[6]=0` 时作为移动控制，在 `sw[6]=1` 时作为视角控制。S5 是动作按键，`sw[5]` 决定动作模式，`sw[4:0]` 决定放置方块类型。为了避免连续误触发，S5 在 VHDL 核心中经过按键去抖、跨时钟同步和上升沿检测，最终形成单周期动作脉冲。

| 控制项 | 功能 |
| --- | --- |
| S1/S2/S3/S4 | 移动模式下控制右/左/前/后，视角模式下控制左右/上下视角。 |
| S5 | 执行一次方块操作。 |
| S6 | 复位。 |
| `sw[4:0]` | 选择方块 ID，推荐范围 0 到 23。 |
| `sw[5]` | 选择放置或挖掘。 |
| `sw[6]` | 选择移动模式或视角模式。 |
| `sw[7]` | 背景音乐静音。 |

### 3.4 时钟域设计

系统主要包含三个时钟域：

| 时钟域 | 来源 | 用途 |
| --- | --- | --- |
| `sys_clk` | Minisys 100 MHz 输入 | 顶层逻辑、蜂鸣器、PLL 输入 |
| `pll_clk` | TFT PLL 输出 | 800x480 TFT 扫描与帧缓冲读取 |
| `pll_clk_1` | 渲染管线 PLL 输出 | 体素渲染管线、控制和存储访问 |

约束文件中将这些时钟设置为异步时钟组，避免 Vivado 对不应按同步单周期分析的跨时钟路径进行错误收敛。显示双缓冲模块承担渲染写时钟和 TFT 读时钟之间的数据边界。

## 4. 主要模块设计

### 4.1 板级顶层模块

正式板级顶层负责将工程与 Minisys 硬件平台连接起来，主要职责包括：

1. 接收 `clk_100m`、S1-S6 和 `sw[23:0]`。
2. 例化 TFT 时钟和时序模块。
3. 例化 FmcPGA 扁平化 VHDL 核心。
4. 连接帧缓冲读地址、读使能和 RGB444 数据。
5. 例化手持方块 HUD 叠加模块。
6. 例化 RGB444 到 RGB323 颜色转换模块。
7. 例化蜂鸣器音频模块。
8. 输出 TFT、LED、数码管关闭信号和蜂鸣器信号。

该模块是板级接口与核心算法之间的集成点，也是工程约束、测试映射和硬件调试的主要观察对象。

### 4.2 VHDL 核心扁平化封装

VHDL 扁平化封装模块的作用是把 FmcPGA 核心从原始顶层中抽离出来，并以简单端口暴露给 Verilog 顶层。原工程中存在 VHDL record 类型、VGA 输出、PS2 手柄接口和七段数码管接口，不适合直接作为 Verilog 顶层实例化对象。扁平化封装保留渲染、地图修改、玩家状态和显示缓冲的核心功能，去除与本开发板不匹配的接口。

该模块还实现了按键控制重映射、视角模式、动作单脉冲、放置/挖掘选择和帧缓冲读接口，是本项目移植成功的关键模块。

### 4.3 TFT 显示模块

TFT 显示链路由时钟生成、时序扫描、读地址映射和颜色转换组成。时序模块产生 800x480 扫描坐标、同步信号和视频有效信号。读映射模块将 800x480 的像素坐标映射到 320x240 源帧缓冲地址。颜色转换模块负责将 RGB444 转换为 TFT 的 8 位 RGB323 接口。

正式顶层对 `video_on`、`hsync`、`vsync` 和 `src_active` 进行寄存，用来匹配 RAM 读延迟和颜色输出时序。TFT 时钟输出采用调试后确定的相位连接方式，保证显示稳定。

### 4.4 渲染管线与存储模块

FmcPGA 渲染核心包含视口扫描、管线入口、管线处理、地图读取、纹理读取、颜色累积和帧缓冲写入。主要数据资源如下：

| 数据资源 | 实现方式 | 说明 |
| --- | --- | --- |
| 地图数据 | RAM + MEM 初始化 | 保存世界方块类型，并支持写入修改。 |
| 纹理数据 | ROM + MEM 初始化 | 保存方块纹理颜色。 |
| 纹理索引 | ROM + MEM 初始化 | 将方块 ID 映射到纹理 ID。 |
| 显示帧缓冲 | 双缓冲 RAM | 保存 320x240 RGB444 帧。 |

源码级 RAM/ROM 替代原 Vivado IP，提升了工程可读性和可复现性。该方式也带来一些性能取舍，尤其是 divider 替代模块使用组合 `/` 和 `%`，会增加综合与时序压力。

### 4.5 音频与 HUD 模块

蜂鸣器模块使用 100 MHz 主时钟产生方波音频，内部包含背景音乐节拍计数、音符选择、交互音效计数和音效优先级控制。放置和挖掘使用不同音效，放置音效还会根据方块 ID 低位产生差异。`sw[7]` 可关闭背景音乐，但不会关闭交互音效。

手持方块 HUD 模块在 TFT 像素坐标位于右下角区域时，用所选方块颜色覆盖原 RGB444 像素，绘制一个简化立体方块。该模块不影响核心渲染帧缓冲，只在输出阶段叠加，因此对核心管线侵入较小。

正式工程创建入口为 `create_fmcpga_tft_project.tcl`，正式构建入口为 `run_fmcpga_tft_build.tcl`。脚本化构建使工程可复现，也便于报告验收时说明构建过程。

### 5.2 板级引脚约束

Minisys 约束文件指定目标板级接口，核心约束包括：

1. `clk_100m` 位于 Y18，采用 LVCMOS33，周期 10 ns。
2. S1-S6 分别映射到 Minisys 对应按键引脚。
3. `sw[23:0]`、三组 LED、数码管、蜂鸣器和 TFT 信号均绑定到开发板对应引脚。
4. TFT 使用 RGB323、`TFT_CLK_O`、`TFT_DE_O`、`TFT_HSYNC_O`、`TFT_VSYNC_O`、`TFT_ADJ_O`、`TFT_MODE_O`。
5. 全部板级普通 IO 使用 LVCMOS33。
6. 配置电压设置为 3.3 V，`CFGBVS` 设置为 `VCCO`。

这些约束决定了工程只能直接运行在指定 Minisys 硬件环境上。如果更换开发板或 TFT 接口，需要重新审阅引脚、电平标准、时钟输入、TFT 时序和配置存储器型号。

### 5.3 时钟与跨时钟约束

工程创建 100 MHz 系统时钟，并将系统时钟、TFT 时钟和渲染管线时钟设置为异步时钟组。这一约束的工程含义是：三个时钟域在物理上可能有关联，但逻辑上不应按同步单周期路径进行直接分析。

跨时钟数据主要通过显示双缓冲读写边界处理。渲染管线写入帧缓冲，TFT 像素时钟读取帧缓冲。按钮输入由去抖模块在管线时钟域处理，S5 动作信号进一步同步和脉冲化。这些设计降低了跨时钟误判和亚稳态传播风险，但仍建议后续对所有跨域边界补充专门 CDC 审查。

### 5.4 工程约束的影响

工程约束对实现产生了以下影响：

1. 显示接口固定为 800x480 RGB323，因此必须进行源帧缩放、居中和颜色截断。
2. 片上资源有限，地图、纹理和双帧缓冲占用较多 BRAM。
3. 目标器件为 Artix-7 系列，DSP 和 BRAM 可以支撑体素渲染，但需要关注长组合路径和乘除法代价。
4. Vivado 2018.3 对 VHDL 2008、混合语言和部分现代写法支持不如新版本，需要显式设置文件类型和编译顺序。
5. 课程演示需要可复现构建，因此脚本优先从源码重建工程，这牺牲了部分增量构建速度。

### 6.4 人工测试步骤

需要人工介入的测试用例如下：

1. TFT 正式画面测试：下载 bitstream 或从 Flash 启动；观察屏幕是否显示 Minecraft 风格 3D 场景；检查画面是否水平居中、左右黑边是否约 80 像素、颜色是否正常；等待数秒确认无持续闪烁或滚屏。
2. 移动模式测试：设置 `sw[6]=0`；依次按 S1、S2、S3、S4；确认画面分别表现为右移、左移、前进、后退；松开按键后运动停止。
3. 视角模式测试：设置 `sw[6]=1`；依次按 S1、S2、S3、S4；确认视角分别向右、向左、向上、向下变化；切回 `sw[6]=0` 后按键恢复移动功能。
4. 方块选择与 HUD 测试：依次设置 `sw[4:0]` 为 0、1、2、3、5、10、15、23；观察右下角 HUD 是否随方块 ID 改变颜色或形态；非推荐 ID 不应导致画面异常。
5. 放置方块测试：设置 `sw[5]=0`；将准星对准可放置位置附近的方块表面；短按 S5；观察准星附近是否新增所选方块；改变 `sw[4:0]` 后再次放置并比较颜色。
6. 挖掘方块测试：设置 `sw[5]=1`；将准星对准可见方块；短按 S5；观察该方块是否消失；切回放置模式后确认行为改变。
7. 动作单次触发测试：短按 S5 应只产生一次动作；长按 S5 约 2 秒不应连续快速放置或挖穿多个方块；保持 `sw[5]` 不动但不按 S5 时不应自动执行动作。
8. 准星目标反馈测试：观察屏幕中心准星；将准星对准实体方块并确认目标反馈；对准天空或空区域时目标反馈应消失或不指向实体；操作对象应与反馈一致。
9. 音频测试：`sw[7]=0` 时等待 3 到 5 秒，确认蜂鸣器有背景音乐；按 S5 确认有短音效；切换放置/挖掘确认音效可区分；`sw[7]=1` 时背景音乐静音但 S5 音效仍存在。
10. LED 测试：观察红、绿、黄 LED；拨动 `sw[7]`、`sw[6]`、`sw[5]` 和 `sw[3:0]`，确认对应 LED 状态变化；按下 S5 时动作状态位应变化。
11. Flash 上电启动测试：完成 Flash 烧录和 verify；关闭开发板电源；按开发板手册设置从 SPI Flash 启动；重新上电且不执行 JTAG 下载；确认 TFT 自动显示正式系统画面，并抽测按键和音频功能。

## 7. 性能与质量指标分析

### 7.1 板子资源利用率

Vivado 实现后资源利用情况如下：

| 资源 | 使用量 | 可用量 | 利用率 |
| --- | ---: | ---: | ---: |
| Slice LUTs | 27,371 | 63,400 | 43.17% |
| Slice Registers | 5,259 | 126,800 | 4.15% |
| Block RAM Tile | 76.5 | 135 | 56.67% |
| DSP48E1 | 52 | 240 | 21.67% |
| Bonded IOB | 70 | 285 | 24.56% |
| BUFGCTRL | 3 | 32 | 9.38% |
| PLLE2_ADV | 2 | 6 | 33.33% |

从数据可以看出，主要资源压力来自 BRAM，其次是 LUT 和 DSP。BRAM 使用超过一半，主要原因是系统需要保存地图、纹理、纹理索引和双显示帧缓冲。LUT 使用约 43%，说明体素渲染中的比较、选择、坐标计算和控制逻辑规模较大。DSP 使用约 22%，主要与坐标、射线、颜色和除法相关运算有关。寄存器利用率只有 4.15%，说明当前设计并不是寄存器受限，而是存储和组合计算受限。

### 7.2 时序性能

实现后时序报告中的关键结果如下：

| 路径类型 | 最差情况 |
| --- | --- |
| 100 MHz 系统时钟路径 | Setup 最差余量约 3.077 ns，无失败端点。 |
| TFT 读显示相关路径 | Setup 余量较大，无失败端点。 |
| 渲染管线关键路径 | Setup 最差余量约 0.979 ns，无失败端点。 |
| Hold 检查 | 最差余量约 0.040 ns，无失败端点。 |

最关键的路径位于渲染核心管线处理过程，数据路径延迟约 132.544 ns，逻辑级数达到 161 级，包含大量 CARRY4、LUT 和 3 个 DSP48E1。这说明渲染管线中仍存在较长组合计算链，虽然当前约束下能够通过时序，但余量不大，后续提升频率或扩大功能时需要优先优化该部分。

### 7.3 显示性能

显示侧采用 800x480 TFT 扫描，源帧为 320x240，显示时 2 倍放大为 640x480。该方案降低了渲染核心分辨率压力，同时充分利用 TFT 的垂直方向显示高度。左右黑边虽然降低了全屏利用率，但避免了非整数缩放导致的图像畸变和复杂插值逻辑，是适合 FPGA 课程设计的工程折中。

### 7.4 鲁棒性

显示鲁棒性主要来自三个设计点：TFT 扫描独立于渲染核心运行，源帧读取区域外输出黑色，同步信号、有效信号和源像素有效标志进行寄存以匹配 RAM 读延迟。潜在风险是跨时钟读写帧缓冲时可能出现短暂撕裂，但双缓冲边界能够降低该风险。

控制鲁棒性来自按键去抖和 S5 单周期动作脉冲。S5 的动作信号经过按键去抖、跨时钟同步和上升沿检测，解决了机械抖动和长按连续触发问题。`sw[5]` 只决定动作模式，不直接触发写地图，因此保持 `sw[5]=1` 不会持续挖掘。后续可进一步为拨码开关增加同步寄存器，以提高严格 CDC 审查下的安全性。

复位鲁棒性方面，系统使用按键复位与 PLL 锁定状态共同决定复位条件，保证 PLL 未锁定时逻辑保持复位。当前仍存在较多异步 reset，后续可逐步改为同步释放复位，以提升 DSP/BRAM packing 和 retiming 空间。

数据鲁棒性方面，地图、纹理和纹理索引由 MEM 文件初始化，不依赖外部软件服务。地图修改仅在有效目标和动作脉冲同时满足时写入，降低误写风险。推荐方块 ID 为 0 到 23，高于该范围的值应在后续通过保底纹理或边界检查进一步增强。

启动鲁棒性方面，工程同时支持 JTAG 临时下载和 SPI Flash 持久化烧录。Flash 流程包含写入、verify 和启动状态读取，便于区分 Flash 内容、配置跳线、启动模式和 bitstream 本身问题。

### 7.5 可维护性与可复现性

工程可维护性体现在边界清晰：板级顶层、TFT 时序、显示适配、音频、IP 替代、VHDL 核心封装和原始渲染管线职责明确。工程可复现性体现在脚本化：工程创建、构建、下载、Flash 烧录、Flash 校验和静态检查均有命令入口。主要不足是单元 testbench 尚不完整，当前更多依赖静态检查、构建报告和人工硬件测试，后续应优先补齐纯逻辑模块和关键控制模块仿真。

## 8. 综合与构建速度分析

### 8.1 实测构建耗时

Vivado 成功构建的主要阶段耗时如下：

| 阶段 | elapsed 耗时 | 说明 |
| --- | ---: | --- |
| `synth_design` | 约 2 分 53 秒 | RTL elaboration、综合优化和技术映射。 |
| `opt_design` | 约 30 秒 | 实现前逻辑优化。 |
| `place_design` | 约 1 分 46 秒 | 布局和物理综合。 |
| `route_design` | 约 2 分 27 秒 | 布线、时序修复和 hold 修复。 |
| `write_bitstream` | 约 29 秒 | bitstream 生成。 |

这说明工程耗时不是单纯由综合造成的，实现阶段尤其是布局和布线同样占据明显时间。

### 8.2 综合速度较慢的原因

综合和实现耗时较长主要有四类原因。

第一，构建流程偏向全量重建。脚本使用强制创建工程和重置 run 的方式保证可复现性，但无法充分利用 Vivado 的增量编译能力。

第二，设计规模本身较大。项目不是简单控制电路，而是包含地图 RAM、纹理 ROM、双帧缓冲、视角计算、射线步进、颜色混合、TFT 输出和音频模块的完整图形系统。

第三，部分 HDL 写法偏算法描述。组合 `/`、`%`、较宽 integer、record 运算和重载函数可读性较好，但综合器需要展开为大量硬件网络。

第四，关键路径较长。渲染核心关键路径达到 161 级逻辑，包含 CARRY4、LUT 和 DSP。长组合路径会让综合器和实现器在优化、布局和布线阶段做更多搜索。

### 8.3 综合速度改进方向

后续可从工程流程和 RTL 结构两方面优化：

1. 区分“全量可复现构建”和“日常增量构建”，日常调试时优先打开已有工程。
2. 非必要时避免重置综合和实现 run，保留中间结果。
3. 引入 checkpoint 或 incremental implementation，让 Vivado 复用已布局布线结果。
4. 使用多线程构建参数明确线程策略。
5. 将组合 divider 替换为流水化 Divider Generator 或自定义多周期除法器。
6. 将角度转换等长条件链改为 ROM 查表。
7. 收紧 integer 位宽，使用明确的 `signed/unsigned` 定点宽度。
8. 给 DSP 相关乘法链增加输入/输出流水寄存器。
9. 减少异步 reset，提升 DSP/BRAM packing 和 retiming 空间。
10. 对渲染管线继续拆分和加深流水，降低单级组合逻辑深度。

这些优化会在一定程度上增加设计复杂度，但可以降低综合和实现压力，提高未来扩展分辨率或帧率时的余量。

## 9. 工程审阅分析

### 9.1 工程优点

从工程审阅角度看，本项目有以下优点：

1. 架构边界清晰：板级顶层、显示适配、音频、IP 替代和 VHDL 核心各自职责明确。
2. 迁移路径稳健：先保留 VHDL 核心运行，再考虑后续 Verilog 转换，降低了一次性重写风险。
3. 脚本化程度较高：工程创建、构建、下载、Flash 烧录、Flash 校验和静态检查均有脚本。
4. 功能演示完整：不仅有画面，还有移动、视角、方块交互、HUD、音频和持久化启动。
5. 需求与测试可追踪：需求编号、测试用例和覆盖矩阵能够支撑课程验收。

### 9.2 风险与不足

工程仍存在一些需要关注的风险：

1. 混合语言增加调试门槛。VHDL record、Verilog 顶层和工具编译顺序都需要谨慎处理。
2. 组合除法和长组合路径会增加综合、布线和时序风险。
3. 异步 reset 较多，可能影响 DSP/BRAM 优化。
4. 拨码输入未完全做同步处理，严格 CDC 审查下仍需补强。
5. 单元 testbench 尚不完整，当前更多依赖静态检查、构建报告和人工硬件测试。
6. BRAM 使用率超过一半，后续扩展地图、纹理或分辨率时空间有限。

### 9.3 审阅建议

后续工程审阅可按以下顺序展开：

1. 先审约束：确认引脚、电平、时钟、异步时钟组和配置电压正确。
2. 再审接口：确认顶层端口、wrapper 端口、RAM/ROM 接口宽度和时钟方向一致。
3. 再审 CDC：检查按键、拨码、显示读写、动作脉冲和复位释放。
4. 再审时序：重点看渲染管线长路径和 hold 修复路径。
5. 再审资源：重点关注 BRAM、DSP、LUT 的模块来源。
6. 最后审测试：补齐 RAM/ROM、mapper、audio、divider 和核心 wrapper 的仿真。

## 10. 人类工程师在 AI 辅助 vibecoding 中的分析方法

### 10.1 AI 辅助开发的价值

在本项目中，AI 辅助或 vibecoding 的价值主要体现在工程整理、快速迁移、脚本化和文档化方面。面对一个已有 VHDL 项目，AI 可以帮助快速识别模块边界，生成 wrapper，整理 Tcl/PowerShell 脚本，补齐 README、需求规格、测试大纲和报告材料。这些工作如果完全人工完成，会耗费大量重复劳动时间。

AI 也适合用于提出候选方案。例如：先混合语言运行还是直接全 Verilog 重写，使用 GUI IP 还是源码替代，先做 smoke test 还是直接接完整核心。这些决策可以由 AI 辅助列出取舍，再由人类工程师结合板级经验选择。

### 10.2 AI 辅助 HDL 的风险

硬件工程中的 vibecoding 不能只看“代码能不能写出来”，还必须看“综合出来是什么硬件”。本项目中一些问题很典型：

1. 软件化表达容易生成昂贵硬件，例如组合 `/`、`%`、宽 integer 和长条件链。
2. 代码看似模块化，但如果跨时钟、复位和 RAM 延迟没有严格审查，硬件行为可能不稳定。
3. AI 可能倾向补齐功能，却忽略 FPGA 资源、时序、CDC 和综合速度。
4. 文档容易写得完整，但如果没有报告数据和硬件验证支撑，会变成不可验收的说明。

因此，人类工程师不能把 vibecoding 当作替代工程判断的工具，而应把它当作加速器。真正需要人类把关的是硬件结构、时序边界、资源代价和测试证据。

### 10.3 人类工程师的分析流程

结合本项目经验，建议采用以下分析流程：

1. 先画结构图，再看代码。确认每个模块的时钟、复位、输入输出和数据流。
2. 先定义硬件边界，再让 AI 写代码。RAM、ROM、divider、CDC、PLL、TFT 时序这类模块必须先明确接口契约。
3. 对 AI 生成的 HDL 做硬件化审查：每个 `/`、`%`、乘法、大 case、for 循环、record 运算最终会变成什么硬件。
4. 每次功能改动都看资源和时序报告，不只看综合通过。
5. 用小 testbench 验证纯逻辑模块，用 smoke test 验证板级显示链路，再接入完整系统。
6. 对跨时钟信号建立清单，逐个确认同步、握手或双口 RAM 边界。
7. 保留可复现脚本和报告摘要，避免只能在当前 Vivado GUI 状态下运行。
8. 把需求、测试和实现建立编号追踪，减少后期报告和验收遗漏。

### 10.4 对本项目的启示

本项目说明，vibecoding 可以显著提高移植和文档化速度，但硬件质量取决于后续工程审阅。若继续优化，应把 AI 用在生成候选重构方案和 testbench 上，而把关键判断留给人类工程师：是否值得把 divider 改为多周期，是否接受更深流水带来的延迟，是否为减少 BRAM 改变地图/纹理组织，是否为增量构建牺牲一部分脚本简洁性。这些都是工程取舍，不是单纯代码生成问题。

## 11. 总结与展望

### 11.1 项目总结

本项目完成了 FmcPGA Minecraft-like 体素渲染器到 Minisys TFT 平台的主要移植工作。系统实现了 3D 体素场景显示、TFT 显示适配、玩家移动、视角旋转、方块选择、放置/挖掘、准星反馈、手持方块 HUD、蜂鸣器背景音乐与交互音效、LED 调试、Vivado 自动化构建、JTAG 下载、SPI Flash 烧录和静态一致性检查。工程具备较完整的需求、测试和报告材料，能够支撑课程设计验收和后续维护。

从实现结果看，系统在 `xc7a100tfgg484-1` 上资源使用处于可接受范围：LUT 约 43%，BRAM 约 57%，DSP 约 22%，实现后时序无失败端点。主要瓶颈是 BRAM 占用和渲染管线长组合路径；主要工程问题是全量构建耗时较长、部分 HDL 写法偏软件化、单元仿真仍需补齐。

### 11.2 后续展望

后续可从以下方向继续改进：

1. 完善单元 testbench，特别是 mapper、RAM/ROM、divider、audio 和核心封装。
2. 引入增量构建流程，减少日常调试等待时间。
3. 将组合 divider 替换为流水化或多周期结构。
4. 将长条件链和近似函数改为 ROM 查表。
5. 对核心渲染管线进一步流水化，降低关键路径逻辑级数。
6. 将异步 reset 逐步改为同步释放，提升时序和资源优化空间。
7. 对拨码开关和跨时钟控制信号补充同步处理。
8. 在混合语言版本稳定后，逐步将小模块和控制模块转换为 Verilog。
9. 优化纹理和地图资源组织，为更大场景或更多方块类型预留空间。

总体而言，本项目已经从“能显示的 FPGA 图形实验”推进到了“具有工程结构、脚本、测试、文档和硬件交互的完整课程设计系统”。后续优化重点不再是简单补功能，而是面向硬件质量、构建效率、可验证性和可维护性的工程深化。
